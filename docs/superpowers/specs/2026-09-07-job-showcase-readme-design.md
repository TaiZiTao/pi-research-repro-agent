# 求职展示版 README 设计

## 1. 背景与目标

当前仓库 README 已能说明项目定位和启动方式，但更接近简要开发说明，尚不足以支撑 Agent 开发岗位的简历核验与面试追问。

本次改写的目标是：让招聘方在较短时间内看懂项目解决的问题、候选人的个人工作、关键技术取舍和可验证结果，同时让技术面试官能够继续定位到实现、评测与复现实验材料。

目标读者按优先级分为：

1. Agent/大模型应用开发岗位的技术面试官；
2. 进行项目初筛的招聘人员；
3. 希望运行或阅读源码的开发者。

## 2. 采用方案

采用“求职展示为主、工程文档为辅”的单页 README：首屏突出价值、个人贡献与量化结果，中段解释系统设计和技术深度，后段提供运行、复现、目录、限制与上游归属信息。

不采用以下两种方案：

- 纯产品宣传型：视觉突出，但不利于核验技术真实性；
- 纯开发手册型：运行信息完整，但核心亮点埋得过深，不适合招聘场景快速阅读。

## 3. 核心信息架构

README 按以下顺序组织：

1. 项目标题与一句话定位；
2. 核心亮点与最终评测指标；
3. 产品截图；
4. 系统架构图；
5. 论文复现八阶段流程；
6. DeepSeek 与 Qwen3-0.6B 的职责边界；
7. MCP、Skills 与论文证据检索；
8. 工具决策模型的训练与评测；
9. 受控执行、安全约束与验收边界；
10. 快速开始与评测复现命令；
11. 目录结构；
12. 已知限制；
13. 个人贡献与上游 Pi Agent Desktop 的关系；
14. License。

## 4. 首屏叙事

首屏必须直接回答四个问题：

- 这是什么：面向科研论文的代码复现 Coding Agent；
- 能做什么：完成论文获取、证据检索、复现规划、代码执行、错误修复与产物验收；
- 与普通聊天助手有何区别：具备显式工作流、工具路由、可追溯证据和受控执行能力；
- 有何结果：展示同一评测集上的动作准确率与过度调用率变化。

首屏不堆叠依赖名称，不使用无法从仓库材料核验的“端到端高成功率”“完全自动复现”等宣传性结论。

## 5. 技术叙事重点

### 5.1 双模型分工

- DeepSeek 始终作为主模型，负责对话、推理、规划与代码生成；
- LoRA 微调的 Qwen3-0.6B 作为本地工具路由器，参与研究工具的选择、参数生成与停止判断；
- Qwen 自主链仅覆盖已启用的只读研究工具，状态变更或高风险操作仍由主模型与宿主安全门控处理。

这一表述用于消除“Qwen 是否负责整个复现流程”的歧义。

### 5.2 工作流与工程闭环

使用流程图展示论文获取、内容解析、证据检索、仓库检验、复现规划、命令配置、受控执行和结果验收八个阶段，并明确失败后最多自动修复三轮。

### 5.3 证据与可追溯性

说明 arXiv/OpenAlex/GitHub 接入方式、三个 Research Skill 的职责，以及 PDF 按页解析和 Dense+BM25 混合检索。强调 Chunk 绑定论文、页码和块标识，从而支持规划与代码生成引用原文证据。

### 5.4 工具路由训练与评测

说明 257 条轨迹、511 个决策样本、Qwen3-0.6B LoRA 微调和 111 条固定评测样本。主结果采用同一 checkpoint/同一评测口径下的最终数据：

| 指标       | 基座模型 | 最终路由模型 |
| ---------- | -------: | -----------: |
| 动作准确率 |   48.65% |       81.08% |
| 过度调用率 |   25.00% |        3.57% |

README 只在需要解释评测严谨性时补充数据划分与 prompt 去重；完整数据链接到 `docs/results.md`。

### 5.5 受控执行与验收

说明参数 Schema 校验、工作区边界、危险命令拦截、敏感信息清理、超时控制、有限次数修复与产物清单。SHA256 仅表述为产物完整性校验，不表述为论文指标或算法正确性验证。

## 6. 视觉与可读性

- 复用 `docs/screenshot-research.png` 作为产品截图；
- 使用 GitHub 可直接渲染的 Mermaid 图展示系统架构和阶段流程；
- 使用一张小型指标表代替长篇评测文字；
- 控制标题层级，避免大段连续文字和过量 badge；
- 中文为主，保留必要的英文技术名词，便于招聘方与源码对应。

## 7. 快速开始策略

快速开始只保留最短可执行路径：环境要求、安装依赖、启动桌面端，以及可选的本地 Qwen 路由服务。更完整的模型准备、训练、评测和排障入口链接到现有文档或明确命令。

所有命令必须来自仓库现有 scripts 或文档，不新增未经验证的启动方式。

## 8. 个人贡献与上游边界

README 单设“个人工作”或“在上游基础上的新增实现”一节，明确项目基于 Pi Agent Desktop 二次开发，并列出候选人新增的研究复现工作流、MCP 获取服务、三个 Research Skill、论文 RAG、Qwen 工具路由训练与接入、执行约束和评测材料。

不将 Electron 桌面框架、通用 Agent 基础设施等上游能力包装为个人从零实现。

## 9. 真实性边界

成稿必须遵守以下边界：

- 仅说明一个小型超分辨率模块有记录的“报错—修复—完成”端到端样例，不扩展为多论文复现成功率；
- RAG 若展示指标，应使用当前 36 条自然语言问题、8 篇论文的结果，并同时保留封闭语料与语言分布限制；
- 工具路由主指标使用 base111 与 overtool111 的同口径对比，不拼接不同 checkpoint 的最优单项结果；
- 明确 Qwen 是工具路由辅助模型，不是主推理或代码生成模型；
- 明确近期事件为进程内观测，不暗示已具备跨重启持久化审计；
- 明确 PDF 页码跳转属于最佳努力能力，不承诺所有查看器均精确定位。

## 10. 验收标准

README 改写完成后应满足：

1. 前两屏可看懂项目定位、个人贡献和量化结果；
2. 双模型职责无歧义；
3. 所有关键数字都能在仓库评测材料中找到对应依据；
4. 启动与评测命令来自现有配置并经过静态核对；
5. Mermaid、图片和相对链接在 GitHub 仓库路径下可解析；
6. 明确陈述限制与上游归属，不夸大自动化范围；
7. 不修改业务代码，仅更新 README 和必要的设计记录。
